# Живая синхронизация bd → канбан-доска

Дата: 2026-07-31
Статус: утверждено, к реализации
Задача в трекере: `smetana-29j`

## 1. Задача

Канбан-доска в `views/DesktopApp.vue` сейчас живёт на фикстурах `views/desktopAppData.js`.
Нужно, чтобы она показывала реальное содержимое трекера **bd** и обновлялась сама, как только
трекер меняется — неважно, изменил его пользователь в интерфейсе, агент в соседнем окне или
человек командой в терминале. Через тот же канал заводятся и правятся задачи.

Приложение целевым образом — кроссплатформенное на Tauri; текущая веб-реализация временна, но
должна остаться работоспособной для проверки компонентов.

## 2. Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Где живёт прослойка | Внутри Tauri, в Rust-процессе приложения | Ни портов, ни отдельного демона, ни авторизации. Один бинарник. |
| Каркас Tauri | Поднимаем сейчас | Первая же реализация боевая, ничего не выбрасываем. |
| Колонки доски | 1:1 статусы bd, встроенные и кастомные | Никакого теневого состояния рядом с трекером. |
| Механизм слежения | fs-watch + инкрементальная догрузка + периодическая страховка | Вызов bd стоит ~1,7 с, опрос по таймеру слишком дорог. |
| Объём записи | Создание, правка в инспекторе, закрытие и переоткрытие | Drag'n'drop отложен. |
| Поставка bd | Вшиваем как sidecar, приоритет вшитому | Приложение самодостаточно, версия зафиксирована, поведение одинаково на всех машинах. |

## 3. Установленные факты

Проверено на машине разработчика 2026-07-31; всё, что ниже, подтверждено запуском, а не
предположением.

**Про bd как таковой**

- Версия в системе — 0.63.3, актуальная — 1.1.2. Репозиторий переехал на `gastownhall/beads`.
- Режим базы — встроенный Dolt (`dolt_mode: embedded`). SQL-сервера нет: `bd dolt status` отвечает
  «not supported in embedded mode». **CLI и есть API.**
- Ни `bd watch`, ни `daemon`, ни `serve`, ни `mcp` не существует — push-канала из коробки нет.
- Отдельный бинарник `dolt` в PATH не нужен: bd отработал с урезанным `PATH=/usr/bin:/bin`.
- Один вызов `bd list --json` занимает **1,5–2,9 с** (старт процесса плюс открытие базы).
  Параллельные вызовы не конфликтуют и не падают на блокировке.
- Любая запись трогает `.beads/embeddeddolt/<db>/.dolt/noms/{manifest,journal.idx}` и
  `.beads/last-touched` — надёжный сигнал для fs-watch.
- Предупреждения (`Warning: dolt auto-push failed`, `beads.role not configured`) идут в **stderr**,
  stdout остаётся чистым JSON.
- У `bd list` дефолтный `--limit 50`; для полной выборки обязателен `-n 0`.
- `bd create --json` возвращает **объект**, а `bd update` и `bd close --json` — **массив**
  (эти команды принимают несколько id). Парсер обязан принимать обе формы.
- `bd statuses --json` отдаёт `built_in_statuses[]` и кастомные с полями
  `{name, category, icon, description}`; категории — `active`, `wip`, `done`, `frozen`.
- `bd list --updated-after <RFC3339>` работает — инкрементальная догрузка возможна.
- `bd close` принимает `-r/--reason`, в том числе по одной причине на каждый id.
- Пустые поля в выдаче опускаются: `assignee` и `labels` появляются только после того, как заданы.
- Родство задач — это зависимость типа `parent-child`, а не отдельное поле. При этом `bd list --json`
  отдаёт и готовое поле `parent`, и полный массив зависимостей с `type`.
- Версия 1.1.2 без ошибок читает базу, созданную 0.63.3 (проверено на копии `.beads`).

**Про бинарник bd**

- Лицензия **MIT** — распространение в составе продукта разрешено при сохранении текста лицензии
  и копирайта.
- Размер — 128 МБ распакованный, 43 МБ в архиве.
- В релизах есть все нужные платформы: darwin arm64/amd64, linux arm64/amd64, windows amd64/arm64.
- Сборка из Homebrew **непереносима**: линкуется на `/opt/homebrew/opt/icu4c@78/lib/*.dylib`.
  Официальный релизный бинарник переносим — зависит только от `/usr/lib` и системных фреймворков.
- Подпись релиза — ad-hoc; при бандлинге macOS его нужно переподписать сертификатом приложения.

## 4. Архитектура

Всё в Rust-процессе Tauri. Фронт общается только через `invoke` (команды) и `listen` (события).

```
Vue (webview)
  DesktopApp.vue → stores/tracker.js → invoke / listen
                                          │
src-tauri/src/tracker/                    │
  commands.rs   тонкие #[tauri::command] ─┘
  service.rs    один tokio-воркер: владеет снимком, сериализует вызовы bd, шлёт дельты
  watcher.rs    notify на .beads/, фильтр путей, debounce
  store.rs      снимок HashMap<id, Issue> + last_seen, вычисление дельты
  bd.rs         единственное место, знающее CLI: аргументы, запуск, разбор, ошибки
  model.rs      Issue, ColumnDef, Delta, TrackerError + serde
```

Границы модулей:

| модуль | что делает | от чего зависит |
|---|---|---|
| `model.rs` | общий словарь; ровно эти структуры видит фронт | ничего |
| `bd.rs` | типизированный запрос → процесс bd → типизированный результат | `model` |
| `store.rs` | `apply_full()` и `apply_incremental()` → `Delta` | `model` |
| `watcher.rs` | файловые события → тики в канал | ничего |
| `service.rs` | склейка: тики и команды в одной очереди, emit событий | всё выше |
| `commands.rs` | переложить запрос в канал и дождаться ответа | `service` |

`store.rs` и `bd.rs` — чистая логика без Tauri и без запуска процессов, поэтому покрываются
юнит-тестами.

**Почему воркер, а не мьютекс на снимке.** Вызов bd стоит ~2 с. Под общим мьютексом команды
интерфейса блокировали бы друг друга на непредсказуемое время. Очередь даёт понятный порядок,
позволяет схлопывать подряд идущие тики watcher и оставляет ровно одно место, где есть изменяемое
состояние — однопоточное по построению.

## 5. Контракт с фронтом

**Команды**

| команда | аргументы | результат |
|---|---|---|
| `tracker_snapshot` | — | `Snapshot { columns, issues, generation }` |
| `tracker_create` | `NewIssue { title, issue_type, priority, description? }` | `Issue` |
| `tracker_update` | `id`, `IssuePatch` | `Issue` |
| `tracker_close` | `id`, `reason?` | `Issue` |
| `tracker_reopen` | `id` | `Issue` |
| `tracker_resync` | — | `Snapshot` |

`IssuePatch` — все поля необязательные: `title`, `description`, `status`, `issue_type`, `priority`,
`assignee`, `add_labels`, `remove_labels`.

**События**

- `tracker:delta` → `{ generation, upserted: Issue[], removed: string[], columns?: ColumnDef[] }`
- `tracker:health` → `{ state: "ok" | "not-a-beads-repo" | "bd-version-mismatch" | "error", message? }`

`generation` — монотонный счётчик снимка. Увидев разрыв в нумерации, фронт вызывает
`tracker_resync` и заменяет состояние целиком.

**Соответствие командам bd**

| операция | вызов |
|---|---|
| колонки | `bd statuses --json` |
| полная выборка | `bd list --all -n 0 --json` |
| инкремент | `bd list --all -n 0 --updated-after <RFC3339> --json` |
| создание | `bd create <title> -t <type> -p <n> [-d <desc>] --json` |
| правка | `bd update <id> [-s|-t|-p|-a|--title|-d|--add-label|--remove-label] --json` |
| закрытие | `bd close <id> --json` |
| переоткрытие | `bd reopen <id> --json` |

## 6. Модель данных и статусы

Колонки строятся из `bd statuses --json`: встроенные и кастомные, порядок задаётся категориями
`active → wip → frozen → done`. В интерфейсе набор колонок нигде не зашит — этого требует и
дизайн-система.

Поля карточки: `id`, `title`, `status`, `priority`, `issue_type`, `assignee`, `labels`,
`parent` → `spawnedFrom`.

**Зависимости считаем по типу, а не по счётчикам.** Родство в bd выражено не отдельной сущностью, а
зависимостью типа `parent-child`, и она попадает в `dependency_count`. Если брать счётчики как есть,
у каждой дочерней задачи на карточке появится ложное «заблокировано 1». Поэтому `blockedBy` и
`blocks` считаются по массиву зависимостей из `bd list --json` с фильтром по типу `blocks`;
`parent-child`, `related` и `discovered-from` в подсчёт блокировок не входят.

**Пустые поля bd опускает.** В выдаче нет ни `assignee`, ни `labels`, пока они не заданы. Значит все
необязательные поля в `model.rs` — `Option` с `#[serde(default)]`; отсутствие поля не ошибка разбора.

**Словарь синонимов статусов.** Статусы bd (`open`, `in_progress`, `closed`) и `RESERVED` из
`components/status/status.js` (`blocked`, `ready`, `running`, `needs-you`, `done`, `failed`)
пересекаются только по `blocked`. Без перевода всё уедет в генерируемые хэш-цвета и потеряет глифы.
Поэтому на фронте — тонкий слой отображения: `open → ready`, `in_progress → running`,
`closed → done`; остальные статусы, включая кастомные, идут в `normalizeStatus` как есть и получают
хэш-цвет с двухбуквенным кодом. bd при этом не трогаем.

Глифы из `bd statuses --json` (`○ ◐ ● ❄ ✓`) **не используем**: глиф и цвет принадлежат `status.js`,
а кастомные статусы по правилам системы обязаны нести код, потому что статус никогда не передаётся
одним лишь цветом. Из bd берём только `name` и `category`.

## 7. Движок синхронизации

1. **Старт.** `bd statuses --json` плюс `bd list --all -n 0 --json` → снимок, `generation = 1`.
2. **Watcher.** `notify` на `.beads/`, интересуют `**/noms/manifest`, `**/noms/journal.idx` и
   `last-touched`; debounce 250 мс.
3. **Тик.** `bd list --all -n 0 --updated-after (last_seen − 5 с) --json` → инкрементальная дельта.
   Запас в 5 секунд нужен потому, что `updated_at` округляется до секунды: пропуск обходится дороже
   повтора, а дифф идемпотентен.
4. **Страховка.** Полный ресинк раз в 60 с и по фокусу окна — ловит `bd delete` и пропущенные
   события; удаления вычисляются как ключи, которых нет в полной выборке.
5. **Собственная запись.** Результат команды сразу кладётся в снимок и уходит дельтой, не дожидаясь
   watcher. Пришедший следом тик даст пустой дифф.

## 8. Поставка bd

Бинарник едет в бандле как sidecar.

- Файл: `src-tauri/binaries/bd-<target-triple>` (имя обязано оканчиваться на triple, узнаётся через
  `rustc --print host-tuple`).
- Конфигурация: `bundle.externalBin` в `tauri.conf.json`.
- Вызов: `app.shell().sidecar("bd")` — нужен `tauri-plugin-shell` и разрешение в capabilities.
- Проблема «приложение из Finder не наследует shell-PATH» при этом исчезает: путь известен точно.

**Бинарники не коммитим в git** — 128 МБ на шесть платформ в репозитории неприемлемы. Вместо этого
`scripts/fetch-bd.mjs`: качает релиз заданной версии с GitHub, сверяет sha256 по `checksums.txt`,
распаковывает и раскладывает под нужные target triple. Каталог в `.gitignore`, запуск — из
`postinstall` и в CI перед сборкой. Версия задана одной константой; на старте приложение сверяет
`bd version` с ожидаемой и при расхождении шлёт `tracker:health` со `state: "bd-version-mismatch"`.

**Приоритет.** Используется вшитый bd. Переопределение — переменной окружения `SMETANA_BD` с путём
к своему бинарнику, для тех, кто осознанно живёт на другой версии. Полноценный экран настроек
появится позже; заводить его ради одного переключателя сейчас не нужно.

**Согласованность версий.** Приложение супервизирует агентов, а агенты в обычном терминале зовут
системный `bd`. Если версии разойдутся, две разные версии будут писать одну встроенную базу Dolt.
Агентам, которых запускает само приложение, каталог со вшитым bd подкладывается в начало `PATH` —
это покрывает основной сценарий. Агенты, запущенные пользователем вручную, остаются вне контроля;
на этот случай и нужен `bd-version-mismatch` в health.

**Лицензия.** MIT обязывает приложить текст и копирайт: `LICENSE` beads кладётся в ресурсы бандла и
упоминается в разделе «О программе».

**Размер.** Бандл вырастает примерно до 140 МБ. Это осознанная цена самодостаточности; прежний
ориентир «~10 МБ» удалён из CLAUDE.md, чтобы следующий читатель не счёл это нарушением по недосмотру.

## 9. Оптимистичность и ошибки

Запись занимает около двух секунд, поэтому интерфейс применяет изменение немедленно, помечает
элемент как «в полёте», по ответу подтверждает, при ошибке откатывает и показывает `Toast`.

Индикация «в полёте» — ступенью поверхности и `data-attention`, **не цветом**: цвет в этой системе
принадлежит статусу.

- Ошибка определяется по ненулевому коду возврата. Предупреждения в stderr ошибкой не считаются —
  без рабочего dolt-remote они будут постоянным фоном.
- Разбор stdout устойчивый: ищем первый `[` или `{` и принимаем как объект, так и массив.
- Нет каталога `.beads` → `tracker:health` со `state: "not-a-beads-repo"` и `EmptyState` в интерфейсе.

## 10. Браузерный dev-режим

CLAUDE.md требует проверять компоненты через `npm run dev` во всех четырёх сочетаниях темы и
плотности и через `?view=gallery`. Чтобы не заводить второй адаптер, в браузере (когда нет
`window.__TAURI_INTERNALS__`) ставим официальный `mockIPC` из `@tauri-apps/api/mocks`, отвечающий на
те же команды текущими фикстурами `desktopAppData.js`. Компоненты знают только `invoke` и `listen`,
ветвлений в них нет — галерея и веб-режим продолжают работать.

## 11. Проверка

Тест-раннера в проекте нет, и CLAUDE.md прямо запрещает его выдумывать. Поэтому:

- **Rust:** `cargo test` в `src-tauri` — вычисление дельты в `store.rs` и разбор вывода bd в `bd.rs`
  на зафиксированных JSON-фикстурах, без запуска процессов.
- **Фронт:** вручную, как предписано — `npm run dev`, четыре сочетания темы и плотности плюс
  `?view=gallery`.
- **Сквозной сценарий:** `npm run tauri dev`, затем в терминале `bd update <id> -s in_progress` —
  карточка переезжает сама, без единого действия в интерфейсе.

## 12. Вне объёма

Drag'n'drop между колонками; несколько репозиториев одновременно; реальные агенты, файлы и логи
(остаются на фикстурах); `events.jsonl` и federation; `dolt push`; WIP-лимиты.

## 13. Допущения и открытые риски

- Проект один — каталог, из которого запущено приложение. Пикер каталога появится позже.
- Раз drag'n'drop не в объёме, статус меняется полем в инспекторе.
- Переход между мажорными версиями bd (0.63 → 1.1) проверен только на чтение. До того как вшитая
  версия станет дефолтом, нужно прогнать запись на копии `.beads` и убедиться, что схема не
  мигрирует необратимо.
- bd развивается быстро; `bd.rs` — единственное место, которое придётся править при смене флагов
  CLI, и это осознанная точка хрупкости.
